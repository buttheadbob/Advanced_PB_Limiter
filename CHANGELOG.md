# Changelog

## 1.3.4.5
- Moves the Quasar 1.7 UI contracts and server pick keys out of `Shared` into the Quasar browser assembly, and `Signals` into the Quasar worker. `Shared/QuasarUiContracts.cs` declares `readonly record struct`s, and Magnetar compiles every file under `Shared`, so MagnetarLegacy (.NET Framework 4.8) failed on `IsExternalInit` and could not load the plugin. The browser and the worker still compile these files; the pick keys use the net10 span-based URI unescape.
- On a Quasar cluster node the Magnetar plugin stays inactive and logs why: a grid moves between the cluster's processes and its programmable blocks' run history and punishments do not follow it, and a node loads the world before plugins start. It loads the cluster's canonical config in memory only, and starts no patches, commands or session handlers. Quasar's Reports and Generate report pages show the plugin as inactive on that server, with the reason, instead of "the world is still loading", and a profile sent to it is refused instead of being sent again forever. After a game update the plugin does not match, the pages say so the same way, a queued profile keeps waiting and is applied once the plugin is updated, and the config is still read so Quasar's editor and the Torch tab show the server's settings.
- The Magnetar and Torch plugins read their config beside the world load instead of before it, and copy the settings into the live config once read. Until then no run is tracked or punished, a command that changes a setting is refused with a "still loading" reply, and the Torch tab saves nothing, so defaults edited meanwhile never replace the file. The limiter starts on the loaded world on the game thread. A load that fails runs on the defaults with saves refused until restart. The Magnetar commands are registered in Init, on the loader thread, as before.
- Commands that change a setting reply once the save has finished, and say when it failed, on both hosts. The Torch Save buttons wait for the save and show "Not saved" when it failed. Torch's Dispose waits for a save already writing and for the last change's save. A tab Torch keeps after a plugin reload no longer throws when used.
- The config file's interrupted-write recovery, Damage rewrite, reads and writes are asynchronous; writes are write-through. Writes and recoveries of one file run one at a time through a gate per file in the process and `<file>.lock` beside it, which stays there and is opened for one holder at a time: a share mode on Windows, an flock on Linux, which also works on a Windows folder mounted into a Linux container. Only a lock file another process holds is waited for, up to 15 seconds, after which the error names it; where no lock file can be made, on a read-only folder or without access, only the gate in the process is used and the log says so once for that folder. Before, the lock file was in the shared temp folder and a missing temp folder made every load wait forever.
- The Torch Reports tab no longer keeps the last tracked player and its blocks after a refresh or a world unload.
- The memory check's startup self-check now covers a generic class instantiated over a value type, including a reference inside its value-type field, and bounds each read to the holder's field bytes. A runtime whose shared `FieldDesc` gives a wrong offset turns the check off instead of reading a wrong field.
- The Quasar profile store disposes its writer and stopping source after the last in-flight change, and the Quasar pages log the full exception when a server, profile or report read fails; the control checks log their failure instead of swallowing it. The Torch Reports live view uses a cached callback and a reused StringBuilder for its per-refresh updates.
- Cleans up the remaining analyzer findings: LINQ and `Exists` in the Quasar worker, XML comment language attributes, PowerShell line lengths, and the loader-only nullable annotation in the Magnetar command module.

## 1.3.4.4

Memory is right aligned with the other figures, so a Recompiles count and a Memory value no longer read as one number, and text on the Settings and Privileged Players tabs follows the theme instead of the selected tab's accent. A saved text report is now a labelled, spaced list per block and player, with wrapped quick stats, instead of one long `||`-separated line per entry.

## 1.3.4.2
- The Torch Reports tab is now a live dashboard: one row object per block and player, updated in place through `INotifyPropertyChanged` instead of replacing both grids' `ItemsSource` on every refresh, and virtualized fixed-height tables. Row objects, memory strings and the two dictionaries are no longer rebuilt every tick, so a 0.5 second refresh no longer rebuilds every WPF container and cell.
- The Report tab shows summary tiles (blocks, active, resting, players, combined run time and average, offences, recompiles and memory), a Show resting filter, a clearer live/paused/stopped state, and a modern shared style for the Settings, Privileged Players and Reports tabs. The live view still pauses while its tab is hidden and defaults to 5 seconds.
- Report reads no longer take a block's sample lock: `RunTimeMSAvg`, `LastRunTimeMS` and `PeekRunTimeMS` are cached for readers. The live view copies blocks and players into reusable lists instead of allocating one per player per refresh, and the cleanup pass reads only the cheap enabled/working flags of resting blocks; a block that runs again refreshes its names and state once. Saved reports still include resting blocks even when the live grid hides them.
- The Quasar pages are a modern client-side dashboard: summary cards, a session trend, server status, search and state filters, paged tables, a block/player details dialog, turn-off confirmations and toasts, CSV export, and remembered view choices. The Profiles page is a two-column layout with the saved profiles on the left and the apply/waiting panels on the right, an apply review step and a waiting-to-apply timeline; the Generate report page shows per-server progress, a report preview, copy, text download and CSV export.
- The Quasar UI is built from Razor, HTML, CSS, inline SVG and small JavaScript modules, uses Quasar's palette tokens for light and dark themes, has no MudBlazor dependency, lets the live view pause polling while the browser tab is hidden, and paginates large tables instead of re-rendering all rows on every poll.

## 1.3.4
- The Torch live view no longer builds its report on the game thread. The 1.3.3 review moved that gather there so it could read a block's names and IsWorking safely; it now uses the names and working state the game thread caches when tracking starts and in its cleanup pass, so the live view gathers on the UI thread again and adds none of its per-refresh work to the simulation. A report's grid and block names, and whether a block is on, can be up to about 5 seconds old; run times, averages, offences, recompiles and memory are as live as before. Limit enforcement still reads the live block state. The Quasar live view builds its snapshot on the companion's thread the same way, without waiting for the game thread; a companion still asks an older server plugin for it on the game thread, as that one reads live block state. The live view uses a DispatcherTimer, so a busy UI no longer queues up refreshes that the game thread then works through in one update; it pauses while its tab is hidden, refreshes as soon as the tab is shown again, and defaults to a 5 second refresh instead of 0.5.
- The local paths for the game, Torch, Magnetar and Quasar builds now live in the gitignored `Directory.Build.props.user`, which `Setup.ps1` writes, instead of `GameBinaries`/`TorchBinaries` junctions and a copied `Directory.Build.props`. The Torch project takes its game and Torch folders from those properties; junctions and other links are no longer made or read, so one cannot be deleted as an ordinary folder and take its target with it. An older checkout that still has them should remove the links themselves (`rmdir GameBinaries` / `rmdir TorchBinaries`), not the folders they point to. `Directory.Build.props.user.example` lists every setting and its default.

## 1.3.3
- The log line about Damage read as Turn Off, for a config read from JSON, names only the setting that held it. Before, it named both instant kill and memory punishments when one had Damage, so an admin could change the other for nothing. A bad value's error now names its setting too.
- An instant kill or memory punishment written as a number in JSON or a Quasar profile is read by the values it had before 1.3.2 (the XML config file only accepts names): 0 Turn Off, 1 Damage (read as Turn Off), 2 Destroy. In 1.3.2, 1 was read as Destroy; in JSON 2 failed the whole config, and in a profile it was kept as a value that acted as Turn Off. The log names a setting that held 1 as such, so it can be set to Destroy if that was meant. Any other number, and a number written as text, is refused.
- In JSON the plugin reads, names are read in any case and with spaces around them, as a profile already did. A Quasar-managed cluster config must save back to the same text, so there only Turn Off and Destroy are accepted.
- The config file rewritten for an old Damage changes by those values only where that can be done on its text, spaces around the word included, which the config could not be read with. A file in another encoding, or a value written as CDATA or a character reference, is rewritten from its XML in its own encoding, as is a file whose text edit would touch anything else. It is written beside the file and swapped in with one rename, on Windows too (through kernel32's MoveFileEx, as .NET's own File.Move with overwrite does), so a crash during the write leaves the old file or the new one. Where it can't be swapped in, it is written in place, and the complete copy beside it is kept until that is done: a config left missing or cut short is restored from it at the next start, and while a missing one waits for that, nothing is saved, so the defaults the server runs on meanwhile can't take its place (one that is there but not whole is first moved to `<name>.cfg.before-restore`, in case it was a hand edit), and a copy that differs from a whole config is kept as `<name>.cfg.damage.tmp.kept` and the log says so; if it can't be moved to that name, the config is not rewritten over it, and on Magnetar no change is saved until the next start, where that copy becomes the config; if the config can't be moved aside either, the log says to move the copy in place by hand. Where it can't be written beside it, a full disk say, the file is left as it was; a config still holding Damage can't be read, so it is then moved aside as one that can't. A failure of this step alone no longer moves a readable config aside. The file is read with DTDs and external entities off. A Quasar-managed server, which reads its config from Quasar, leaves this file alone.
- A config that can't be read is moved aside to `<name>.cfg.unreadable`, or a name with the time when that is taken, and the log says so. A config that can't be opened or read for the file system, held by another program say, is left where it is: the server runs on the defaults and saves nothing over it until it restarts, and the log says so. Before, the defaults the server then ran on were saved over it at the next change. The config the first Magnetar build kept in the user data folder is not read in its place, and the log says so at each start until the file set aside is fixed and put back, or the set-aside files are removed and the server restarted before any setting is changed (a change saves the defaults as the new config). Where it can't be moved, nothing is saved over it until the server restarts.
- A save that fails is reported: CreatePrivilegedUser, AllowStaffCommands, DenyStaffCommands, Enable, Disable and debug say so in their reply, the Torch Save button and privileged players tab show a message, and a Quasar profile is applied only when it can be saved: otherwise the settings stay as they were, the reason goes to the server log, and Quasar keeps the profile queued with that reason and sends it again; the server logs the reason once, and again only if it lasts past 10 minutes, not on every try. A node of a managed cluster refuses a profile for good: its settings come from the cluster's plugin configuration, which Quasar changes only for the whole cluster. For the same reason it refuses Enable, Disable, debug, AllowStaffCommands, DenyStaffCommands and CreatePrivilegedUser, which would change that one node until it restarts.
- A block dropped from tracking after "keep inactive pb duration" (30 seconds by default) without running comes back as it was on its next run, with its runs, offences and startup time, and that run is checked. Meanwhile it still counts for the commands and requests that cover a player's or the server's blocks: turning a player's blocks off from Quasar, turning one block off, the shutdown warning to scripts, the memory check and the reports. Before, a script started less often than that was tracked again as new each time, in a new startup time, so its runs were never checked. Its run times are not added to a player's combined run times in the reports, as the combined limits leave it out (the reports' combined run times count the blocks the combined limits count (from 1.3.4 the reports use the state cached by the last cleanup pass, so they can trail the limits by up to about 5 seconds; the limits still read the live state), leaving out blocks still in their startup time, and blocks that cannot run (off, damaged or unpowered) unless they ran since the last combined check and were not turned off by the limiter or an admin after that run), nor counted for the hottest block, and the reports and Runtimes mark it as resting. A recompile starts it over when "clear data on pb recompile" is on, as for a tracked block. Such a block is forgotten when it is removed or has not run for "keep player data with no pbs" (60 minutes by default). A block that changes owner moves to its new owner's tracking with its run times, offences and startup time; one given to nobody or to an ignored NPC keeps them for the next tracked owner, until it has not run for "keep player data with no pbs". In survival the game stops a script when its block changes owner, so the new owner has to recompile it, and with "clear data on pb recompile" on, as by default, that recompile starts the block over with a new startup time, as any recompile does; with it off, or in creative, where the script keeps running, the block keeps its history.
- A damage amount of 0 turns the block off, as it can't damage anything; it is not treated as a protected block. Damage on a block the game won't damage turns it off, or with "destroy protected PB" on removes it as before, instead of doing nothing while "was punished" repeated on every offence. This is checked as the game checks damage: in a safe zone or a world that forbids it at the block's position, on a grid or world with block destruction off, and where the grid's or block's damage modifier is 0. Destroy removes such a block as it did one in a safe zone, and otherwise takes the damage modifiers into account, so it stops at 100 integrity on every grid. Before, the first safe zone whose box touched the block decided, enabled or not.
- A disabled limiter no longer keeps a block that is turned off from turning on with a recompile, as it no longer does on a run.
- No run of a script's Main is left out any more: each is charged the game's own wall time for it, as before (less the sim-speed discount when "Use SimTime" is on), less the runs it made of other blocks through TryRun, which are charged to those blocks instead of to the block that called them. Before, a run a garbage collection happened in was left out altogether, so a script that set off a collection in its runs (a large allocation, say) escaped every run-time limit and the instant kill. Such a run now counts for the run-time, average and combined limits like any other (the run-time limit and the average pass over a run that stands out from the block's last 50 runs, as they do for every run); only the instant kill passes it over, as the collection can hold every thread still for longer than the script ran, and nothing on .NET Framework tells that pause apart from the script's own time. A script's constructor and Save() are not measured, as before, and neither is the step that creates its instance after a recompile, which before was counted as a run with the old script's last time.
- A script that turns its own block off at the end of each run, and is turned on and run again by a timer or another block, is checked like any other: an instant kill is applied once for the runs queued in one tick by remembering that tick, not by whether the block works, and such a block counts in the combined run times while it has run since the last combined check, counted in game ticks as the check is. A block the limiter or an admin turned off stops counting at once. A block owned by nobody, which is not tracked, has its script ended as well as being turned off when "Turn off when owned by Nobody" (TurnOffUnownedBlocks on Magnetar) is on, so another block can't turn it on and run it. The memory check also measures what a script holds through Linq iterators and MyIni. As before, it does not measure what a script holds in static fields: finding them would load every type of the script, which a script can make take minutes. It reads a script's fields without loading the types they are declared with, so a field of a type the runtime would take long to load (a class at the end of a long chain of classes, or an array of arrays thousands deep) costs it nothing; on a .NET runtime where it can't read fields that way, the check does not run, no memory limit is applied, and the log says so once. It runs only while the limiter is on. A script the check can't measure never stops the check for other blocks, and with a memory limit set counts as over it: one whose structs nest more than 255 deep (256 for a struct held in an array), one with a type the runtime fails to load while the check reads it, or, with a limit set, one holding more than the walk's budget can follow. The budget is twice what the limit needs: every object, every element of an array of references (multi-dimensional ones too), every delegate list entry and every reference in a struct an object holds is a step, and a struct boxed out of an array a step per 8 bytes with every reference inside it read within that charge, so it bounds the time a scan takes. The log says which case once for that block, the instant-kill log and chat say its memory was not measurable, and the Torch Reports tab, its saved report and the Quasar pages show "not measurable" in place of a size, a player's total as the measured blocks "+ not measurable", and the Quasar pages sort such blocks and players as the largest. With no limit set, a scan that runs out of budget shows what it walked, a lower bound. If the server itself runs out of memory during a scan, or the check fails on a block in a way it does not know to be the script's, the block keeps its last figure, the log says so once for that block, and the next pass tries again; if the check's thread can't be started, every block keeps its last figure and the log says so once. A delegate's invocation list is counted in full; before, a delegate doubled into millions of entries counted as one. The scan runs on a thread of its own. Before, structs nested a few thousand deep ran the walk out of stack, which ends the server process, and one script's type that could not load stopped the check for every block. A protected block removed by Destroy is re-sent only to the players who see it, found by its entity id; before, it was matched by its name, which its owner chooses, and could re-send other players' blocks.
- A grace period longer than about 24 days is cut to that, the most a delay can wait. Before, a longer one failed and the block was never punished again. A punishment waiting out its grace period is dropped if the limiter is disabled meanwhile, even for a moment, or its world reloads. A block handed to someone else during its grace period is still punished, once, and its new owner is told why. An instant kill, by run time or by memory, is applied at once also while a block waits out the grace period of an ordinary punishment, and takes its place: the harsher of the two is applied, once (Destroy over Damage over Turn Off, and Damage then also turns the block off, as an instant kill always stops the script); before, the instant kill waited for that punishment. A compile forgets the old script's memory use, also while the limiter is off, so the new script is not instant-killed on the old figure, and the recompile count shown in the reports counts every recompile of a tracked block made while the limiter is on, also with "clear data on pb recompile" off. Limits leaves out the combined limits when the server does not check them, and says so.
- Two MyStats requests sent at once no longer both pass the 30 second wait. CreatePrivilegedUser and Quasar profiles refuse limits that are not numbers and punishments that don't exist, which made every later save fail; a profile with a value outside a setting's range, or that can't be read, is refused for good and shown so in Quasar instead of being sent again, and a server whose config holds one says so when it is saved as a profile. Limits shows "no limit" for a limit of 0. A second Timings request within 5 seconds is no longer cut short by the first.
- Magnetar removes its own patches when it shuts the plugin down, and only its own. If a patch fails to apply, the others are removed again and the plugin stays inactive. The plugin needs Magnetar 2.4.2.1 or later: it reads PluginSdk's ManagedPluginConfiguration, first in that version, to tell a node of a managed cluster, and an older Magnetar can't compile it.
- Numbers in chat replies, reports and log lines are written the same on every server, with a decimal point. Before, a server set to a culture with a decimal comma wrote some values as 0,1234 and others as 0.1234. Names that scripts and players choose (blocks, grids, players) have control characters, line breaks, Unicode format characters (such as bidi overrides, zero-width and tag characters) and characters the server's .NET does not know replaced with spaces in logs, chat, reports and the Quasar pages, and a name longer than 100 characters is cut to at most 100 (99 where the 100th would split a character) followed by "...", so a name can't forge log or report lines. Runtimes can be asked once every 30 seconds, as MyStats, and lists at most 10 blocks; MyStats lists at most 20 and GetReport at most 200 blocks in detail, and their totals count all of them.
- Torch: a save that fails, the file held by another program say, is tried again every 30 seconds until it saves, and the log says so once per reason and again when it is saved. While saves are refused (a config that could not be opened when Torch started, one that could not be read and could not be moved aside either, or a missing one whose copy waits to be restored), nothing is saved or tried again until Torch restarts, and the log says so when a save is asked for. The config is saved through a complete copy swapped in with one rename, one save at a time, also when a plugin reload leaves an old instance of this version saving. A crash during a save leaves the old file or the new one; a file left cut short is restored at the next start (the file that was there is first moved to `<name>.cfg.before-restore`, in case it was a hand edit), and a complete copy that differs from the config is kept as `<name>.cfg.tmp.kept` and the log says so. A config another program holds when Torch starts is left alone instead of being moved aside as unreadable: Torch then runs on the default limits and privileged players until a restart, and saves nothing over it. A game update that changes a method the limiter patches leaves the limiter inactive instead of stopping Torch from starting; its commands and the plugin's tabs then say so, and its settings are not saved until Torch restarts. MyStats, Runtimes and GetReport reply on the game thread. The Reports tab's combined average is the sum of the blocks' averages, as in chat and Quasar, instead of their mean. A saved report names the hottest player by run time per tracked block, as chat does, not by the sum. The Reports tab only accepts a refresh rate from 0.1 to 3600 seconds, with a dot for decimals, stops its live view and drops the old blocks when the world stops, and a saved report gives its time with the server's UTC offset and says why when it can't be saved. The privileged players tab refuses a Steam ID of 0, limits that are not numbers or are negative, and a comma in a limit, which could mean a thousand or a decimal point. A config that can't be read is moved aside as on Magnetar, and a config file holding no config no longer stops Torch from starting. A plugin reload, which Torch does not fully support, turns the limiter off until Torch restarts: the old instance stops with its patches, its commands say so, and the log says so. Only a reload does this: a Torch that disposes its plugins as it shuts down stops the limiter without the reload warning. Before, the old instance kept collecting runs that were never checked, and its other patches kept working from a config that no longer changed. The build creates the Build folder for the plugin zip.
- Quasar: a profile change is saved before the page shows it as done, and the page says when it could not be saved; a failed save removes its temporary file. A change made while Quasar is still starting is kept, and a profiles file that can't be read is never replaced by an empty one. A queued profile can no longer be cancelled once it is being sent, and the page says so. A profile whose answer reaches Quasar after it stopped waiting, so that Quasar sends it again, is not applied a second time while the server keeps running: the server answers the repeat as it answered the first (it keeps the last one in memory, so a restart in between applies it again). One answered by a node of a managed cluster that was replaced before the answer was recorded is sent to the new node, as what the old node applied went with it; on a cluster Quasar does not manage, whose nodes may share one config file, the new node may already have it and then gets it a second time. A server never starts a request that changes something or reads a report after the time it allows, a few seconds before Quasar stops waiting, so a request still waiting then is not run late, and the page is told it was not run. One the server started just in time can still finish after Quasar stopped waiting, and one may arrive just before the server's connection drops: the page then says the server may have done it, and a queued profile is sent again, which the server applies at most once. A profile a cluster node refuses, as a node of a managed cluster does, is shown with the reason and not sent again; cancelling removes it, and queueing it again sends it once more. A profile queued for a cluster node reaches it after the node restarts, under the new id Quasar gives it, also when the new node connects before the old one is gone, and never after a newer one, nor twice when it was queued for both the old and the new node (which request is newer is decided by the order they were queued in, not by the clock, so a clock set back, after a virtual machine resumes say, no longer drops a newly queued profile, and a profile dropped because a newer one was already applied, or waits in its place, is written to Quasar's log); a profile queued before 1.3.3 for a node that is offline does not, as the cluster was not saved then. Offline servers can be forgotten from the Profiles page, which shows when each was last seen. The report page says that only the 5 newest reports stay available. A ticked cluster node that restarts stays ticked under its new id, on the Profiles page and the report page, so it is neither dropped nor reported as offline. Names and lists match and sort the same way on every server, and report file names and times are written the same everywhere. A request that fails on the server is written to the server log once per reason for each kind of request, and again only after 10 minutes, so a profile resent while reports keep working, or reports that fail with two reasons in turn and between successes on a lagging server, are not logged again on each try. The profile queue, the Live view and the report page log to Quasar's log the same way, the two pages once for everyone who has them open. A request carries the time Quasar stops waiting for it, so a server refuses one that reaches it later, after waiting behind another request say, instead of turning blocks off or applying a profile after Quasar stopped waiting for it. This relies on the server's clock not being ahead of Quasar's by nearly the whole wait (a request waits 10, 15 or 20 seconds, and is refused from 9, 14 or 19 seconds ahead); a clock behind Quasar's lets a request held up on the way start up to that much later than Quasar waits. The companion looks for the limiter only in newly loaded assemblies once it has searched those loaded at start.
- `build.bat` and the setup script are now `build.ps1` and `Setup.ps1`, run from PowerShell, with the same arguments. On Linux and macOS, `pwsh ./build.ps1 magnetar` (or `quasar`) builds with PowerShell 7; Torch builds on Windows only, and is skipped there with a message. The version step stops the build if it can't update every version file, and a missing tool fails the build.
- Quasar 1.7: the Live view, Profiles and Generate report pages are a browser assembly for the WebAssembly dashboard. The worker adapter registers the authorized SDK operations for the companion channel and the profile store. Quasar 1.7 or later is required; a report is built and downloaded in the browser, so no report files are kept on the server. The build takes a Quasar 1.7 Quasar.Plugin.Abstractions.dll through `-QuasarAbstractions` or `QuasarPluginAbstractionsAssembly` in `Directory.Build.props`, or a 1.7 checkout in `..\quasar`.

## 1.3.2
- Instant kills, by run time and by memory, now offer only Turn Off and Destroy. With Damage the script kept running, so every run over the limit dealt damage again, logged an error and messaged the owner, up to 60 times a second for a script on Update1; in a safe zone with damage off it never stopped. Ordinary offences keep Damage and their warnings as before.
- A config, a Quasar-managed config or a Quasar profile that set Damage for either is read as Turn Off, the default, and the log says so once. Set Destroy again if that was meant.
- Magnetar servers updating from 1.3.0, where instant kills and the memory limit always destroyed the block, run with Turn Off for these two settings: Magnetar's config only holds a value that was chosen, and 1.3.0 had none. Admins who relied on Destroy should set it in Quasar. A Destroy chosen in 1.3.1 is kept.
